Factory Inventory Management System

A demo-scale, full-stack inventory and order analytics application. A Vue 3 single-page app talks to a FastAPI service over plain HTTP; the service reads a fixed set of JSON fixtures into memory at import time. There is no database and no persistence layer.

Request data flow

What happens between a user changing a filter and a repainted chart. This path is the same for every view; only the endpoint differs.

  1. Filter change in the shell
    FilterBar.vue is v-model-bound to refs declared at module scope in useFilters.js. Because those refs live outside the factory function, every importer shares one instance — a deliberate singleton, not per-component state.
  2. Views react
    Each view watches the shared refs and re-runs its loader. No event bus and no store are involved; reactivity alone propagates the change.
  3. Filters are normalized
    getCurrentFilters() maps UI names to API names — notably selectedLocation becomes warehouse — and only attaches month when a period is actually selected.
  4. Query string is built
    src/api.js assembles URLSearchParams and drops any filter whose value is 'all', so a sentinel never reaches the backend. This is the single place the base URL http://localhost:8001/api is defined.
  5. FastAPI binds query params
    Handlers declare each filter as Optional[str] = None, so an omitted parameter is simply None and skipped.
  6. In-memory filtering
    apply_filters() chains list comprehensions for warehouse, category and status; filter_by_month() handles both a direct YYYY-MM prefix match and quarter keys expanded through QUARTER_MAP. Source lists are never mutated — each step rebinds a new list.
  7. Pydantic validation on the way out
    Typed endpoints declare response_model, so a fixture that drifts from its schema fails here rather than silently reaching the browser. Aggregate and spending endpoints return bare dicts and are unvalidated.
  8. Render
    Axios resolves into raw refs (allOrders, inventoryItems); every derived figure — totals, groupings, SVG geometry — is a computed, so it recomputes only when its dependencies change.

The global filter system

Four filters live in the shell and apply across views, but not every endpoint honors every filter — the data model constrains which are meaningful.

Filter UI ref Query param Accepted values Honored by
Time Period selectedPeriod month YYYY-MM or Q1-2025…Q4-2025 Orders, Dashboard summary

Design constraint
Inventory records carry no date field, so /api/inventory deliberately accepts only warehouse and category. A period selection silently does not narrow inventory results — expected behavior, not a defect.

Observations worth knowing

Findings from reading the current source. These are characteristics of the demo, not a to-do list — but they explain behavior that would otherwise look surprising.

Client calls routes the server does not implement
src/api.js defines getTasks, createTask, deleteTask, toggleTask, createPurchaseOrder and getPurchaseOrderByBacklogItem, targeting /api/tasks and /api/purchase-orders. Neither path exists in main.py. The task methods are called from App.vue, so those interactions fail at runtime. The backend does define PurchaseOrder and CreatePurchaseOrderRequest models and loads purchase_orders.json, but exposes no route for them — a half-landed feature.
One summary figure ignores the filters
In /api/dashboard/summary, total_backlog_items is computed from the unfiltered backlog_items list while the other four figures respect the active filters. The backlog count therefore stays constant as filters change.
An unrouted view
views/Backlog.vue is fully implemented but absent from the router in main.js, so it is unreachable. Backlog data reaches users through the Dashboard's table and BacklogDetailModal instead.
Quarter logic is duplicated
filter_by_month() resolves quarters through QUARTER_MAP, while /api/reports/quarterly re-derives the same quarters with an inline if/elif chain over month substrings. Both hard-code calendar year 2025.
Deliberately local-only
Wildcard CORS, no authentication, no rate limiting, a hard-coded localhost API base URL, and a mock user in useAuth are all intentional for a demo. They are also precisely what must change before any deployment.

Running the system

Backend

  • cd server && uv run python main.py
  • Serves on http://localhost:8001
  • Interactive OpenAPI docs at /docs
  • Fixtures load at import; edits require a restart

Frontend

  • cd client && npm install && npm run dev
  • Serves on http://localhost:3000
  • Calls the API directly — no dev proxy configured
  • Backend must be running or every view errors

Tests

  • cd tests && uv run pytest backend/ -v
  • Covers dashboard summary, inventory, and the remaining endpoints via FastAPI TestClient
  • No frontend test suite exists; browser verification is done through Playwright
